## Data and fetching
- **Real scale.** `community-plugins.json` lists 9,385 plugins (not the ~3k the brief assumed). Everything is sized for that: a snapshot is about 106 KB gzipped without GitHub metadata, and a full GraphQL refresh is about 94 batches of 100 repositories.
- **Snapshot content.** Per plugin: `dl` (downloads, cumulative) and `rel` (date of the latest release, which `community-plugin-stats.json` reports as `updated`), plus the optional GitHub fields `push`, `crt`, `arch`, `stars`, `iss`, `fr`, `gone`, `chk`, `src`. Weekly growth is never stored; it is the difference between two snapshots. Plugin ids are written in sorted order and gzip is deterministic, so re-running a week with the same inputs gives the same bytes.
- **`rel` is a free maintenance signal.** It is available for every plugin without any GitHub call, so the analysis always has "last release" even in a week where GitHub metadata could not be refreshed. `push` (last push) is the stronger signal the brief asks for and is used whenever it is present.
- **Never rewrite past snapshots.** `buildSnapshot` writes only the file for the requested week, atomically. Re-running a week overwrites that week only; `score` R1 checks with git that no older snapshot was modified.
- **Rolling refresh (the rate-limit design).** GitHub metadata is refreshed in priority order until the budget or rate limit runs out; the rest keeps the values from the previous snapshot (or from this week's earlier partial run) and the snapshot records `refresh.state = "rolling"` plus how many are pending. A rate limit, a bad token, a missing token or a 502 never fails the build. The order (tier 0 first):
  0. plugins new since the previous snapshot (never checked);
  1. maintainer-wanted candidates (downloads at or above the threshold and no release for 12 months or more), so the headline list is always verified against GitHub first;
  2. plugins never checked;
  3. plugins whose last check was the REST bootstrap, so they gain the feature-request count when GraphQL is available;
  4. everyone else, stalest check first;
  5. plugins already refreshed this week by an earlier partial run (so a re-run continues instead of repeating).
- **GraphQL batching.** 100 repositories per request using aliases (`r0..r99`), and two fragments: `Core` for everyone and `Labels` (open issues with a feature-request-like label) only for plugins at or above `labelsMinDownloads`, to keep the query cost low. On HTTP 502 the batch is halved. The query is validated in tests against a pruned copy of the real GitHub schema (`fixtures/graphql/github-subset.graphql`, made from the published schema by `scripts/make-fixtures.mjs`), and a mock server reproduces NOT_FOUND, rate limits (GraphQL error, HTTP 403, HTTP 429) and 502s.
- **Feature-request labels** are matched by `/feat|enhanc|request|idea|suggest|wish/i`: GitHub label names are free text, and an exact list would miss `type: enhancement`, `feature-request`, `💡 idea` and so on.
- **REST fallback (`--transport rest`).** Used only for local development and for environments where GraphQL is unreachable but the REST API is. It records `src: "r"`, its `iss` includes pull requests, and it has no feature-request count; the planner puts such records first (tier 3) as soon as GraphQL works. The weekly workflow uses GraphQL with the repository's own `GITHUB_TOKEN`.

## GitHub access in the build sandbox (important)
- The sandbox that built this project reaches `raw.githubusercontent.com` (so the Obsidian files) and `forum.obsidian.md`, but its proxy refuses `api.github.com/graphql` and refuses the REST API for any repository other than the one attached to the session. So **the live GraphQL path has never run against real GitHub**. What backs it instead: validation of the query against the real GitHub schema, a mock server with the failure modes above, and the REST field mapping checked against the one repository that is reachable.
- Consequence for the first real snapshot (`2026-W43`): it has complete downloads and release dates for all 9,385 plugins and **no GitHub metadata** (`refresh.state = "rolling"`, `transport = "none"`, 9,385 pending). This is the documented rolling-refresh state the ladder accepts instead of 95% coverage. The first scheduled run on GitHub Actions (which has a token and API access) will start filling it: it does the maintainer-wanted candidates first, and the full list within a few runs at most.
- Consequence for the analysis: wherever `push`/`iss`/`arch` are missing, abandonment falls back to `rel` and the entry is shown as *provisional* ("not yet verified against GitHub") on the site. Nothing is invented.

## Analysis (growth, newcomers, maintainer-wanted)
All analysis is plain arithmetic in `lib/growth.mjs` and `lib/abandonment.mjs` (pure functions, no I/O, no network, no LLM; `score` R2 checks that). Every threshold lives in `config.json` and the Methodology page prints those same values.
- **"Now" is the capture time of the newest snapshot**, not the wall clock, so the same snapshots always give byte-identical analysis (and tests do not rot).
- **Weekly delta** = difference between the two newest snapshots, divided by the number of ISO weeks between them (minimum 1), so a skipped week is averaged instead of shown as one huge week. **Relative growth** = that delta over the previous total.
- **Relative ranking needs a base** (previous total >= 200 downloads and gain >= 20): without it "1 -> 3 downloads" would be +200% and bury everything real.
- **A total that goes down is an anomaly**, not negative growth: it is counted, shown nowhere in rankings.
- **4-week trend** = the per-week gains of the last four intervals; direction compares the recent half with the earlier half ((recent+1)/(earlier+1) >= 1.25 is up, <= 0.8 is down, both halves under 5 downloads/week is flat). Needs three snapshots; before that the site says "needs more history" instead of guessing.
- **Newcomer age** (the brief says "under 90 days old" but history starts at our first snapshot):
  1. a plugin that appears in a later snapshot is *exactly* dated: "first seen" = capture day of the first snapshot that has it;
  2. plugins already in the first snapshot have unknown listing dates, so the date is *estimated* from list order: `community-plugins.json` is append-only (newest last), and the 25th percentile of the latest-release dates of the neighbouring 80 entries is a local clock (a median would lean too recent, because most plugins keep releasing after they are listed). This is labelled "estimated" and is good to roughly two weeks; it matters only for the first weeks, after which every new plugin is exact;
  3. when GitHub metadata is present and the repository was created *after* that estimate, the repository creation date wins (a repository cannot be older than the plugin that lives in it).
  Real numbers on 2026-W43: about 3,300 of 9,385 plugins are under 90 days old by this estimate, i.e. the directory roughly doubled in a quarter; that is why "rising newcomers" is a ranking and not a list.
- **Rising newcomers** are ranked by *momentum*: this week's downloads when we have a previous snapshot of the plugin, otherwise downloads per week since listing (for plugins listed this week that is simply their downloads so far). Zero momentum is not "rising".
- **Maintainer-wanted = gates + score** (formula printed in `lib/abandonment.mjs` and on Methodology). Gates: downloads >= 10,000; quiet >= 365 days; not archived; repository exists; open issues >= 5 *when known*. Quiet is measured from the **later of last push and latest release**: a plugin that shipped a release recently is not quiet even if the repository was not pushed, and the other way round. Score = 40% how loved (log scale 10k to 1M downloads) + 30% how long quiet (12 to 36 months) + 30% open issues (log, 100 issues = full). While GitHub metadata is unknown, the issues part is dropped and the other weights are rescaled, and the entry is flagged **provisional**.
- **Why an open-issues gate at all:** a popular plugin with no activity and no issues is most likely *finished*, not orphaned. Asking for at least five open issues separates "people are waiting for something" from "it does its job".
- **Archived and unreachable repositories are listed apart** ("archived by their authors", "repository no longer reachable"): the brief's list is the not-archived ones, but an archived plugin with 500k downloads is exactly where a successor is welcome.
- **Respectful framing** is a rule for the site, not only a tone: the heading is "Looking for maintainers / room for an alternative"; entries say "no release for 31 months" (a fact) and never "dead", "abandoned" or "unmaintained"; **author names are not shown on that page** (the plugin detail page shows the author because the directory does, as a link to the repository). Quiet does not mean a failing: many authors finished a tool and moved on.
- **Fixtures for the analysis**: `fixtures/snapshots/2026-W43.json.gz` is the real W43 snapshot restricted to the 168 plugins of `fixtures/releases`; `2026-W42.json.gz` is **synthetic** (labelled so in `refresh.note`), derived from it by `scripts/make-fixtures.mjs snapshots` using `fixtures/snapshots/plan.json`: a few planted gains (biggest absolute, biggest relative, a base of 1 download, a gain exactly at the threshold, a falling total, plugins that are new this week, ghosts that were removed). Everything not in the plan gains at most 0.05% by a hash of its id. Tests and `score` read the plan for their expected answers and also recompute independently with plain loops.

## Forum feature requests and gaps
- **Source and politeness.** Discourse's public JSON: `/c/{slug}/{id}/l/top.json?period=yearly|all&page=N` (the most-liked requests first) plus the first pages of `/c/{slug}/{id}.json` (latest). Two categories: *Feature requests* (id 8) and *Plugin ideas* (id 10). One request at a time, 1.1 s apart, about 28 requests per run, with the project's User-Agent. A 429 waits for `Retry-After`; three failed requests in a row stop the run.
- **Optional by construction.** `scripts/forum.mjs` always exits 0 (unless `--strict`). Any failure keeps the previous `data/forum/topics.json` untouched and records the outcome in `data/forum/status.json` (`ok | partial | too-few | failed`). A run that returns fewer than half of the previous topics is `too-few` and does not replace the data (a half-broken listing must not erase the history). Without forum data the analysis, `ideas.json` and the site still build, with an empty Gaps section that says why. Tested against a mock Discourse (`tests/helpers/mock-discourse.mjs`) that serves the raw shape of the real API.
- **What is kept per topic:** id, title, slug, category, created and last-activity day, views, likes, posts, tags, closed, url. No post bodies and no user names: only titles and counts are analysed and linked.
- **TF-IDF, not embeddings.** Plain arithmetic in `lib/text.mjs` (lower-case, stop words including words every request contains such as "add", "support", "plugin", a 20-line suffix stripper, sublinear tf, idf = ln((N+1)/(df+1))+1, L2 norm, cosine). Topics (title and topical tags) and plugins (name twice plus description) share one idf computed over both. Deterministic and explainable, and the brief asked for no LLM.
- **Coverage per request, then per cluster.** Clustering the requests and comparing the cluster *centroid* with plugin descriptions was tried first and rejected: a centroid of a loose cluster resembles no single plugin, so every cluster looked like a gap. Now each request gets its own `fit` = highest cosine with any plugin (found through an inverted index, 9,385 plugins in about a second), and a cluster's coverage is the mean of its requests' fits weighted by demand (1 + likes). Calibration by reading real matches: true matches score 0.5 and above, noise stays under about 0.45. Hence `coveredAbove` 0.5 and `gapBelow` 0.35.
- **Clusters.** Leader clustering in descending likes order (a request joins the most similar centroid if cosine >= 0.45, else starts a cluster), then two refinement passes moving each request to its nearest centroid. 0.3 (first try) glued unrelated requests through shared generic words; 0.45 gives coherent clusters (Bases, Graph view, Canvas drawing, PDF export, tab groups, tags). Clusters below 2 requests are kept only when that single request has at least 50 likes; the dropped count is reported.
- **Meta tags are ignored** (`gaps.ignoreTags`: valuable, ui-ux, mobile, ios, android, upstream-bug...). They describe the request's status, not its subject, and made unrelated requests look alike.
- **App-level flag.** About a third of the most liked requests ask for changes to Obsidian itself (WYSIWYG mode, portable mode, Sync, Publish, mobile). A plugin cannot always deliver those, so clusters whose requests mostly match `gaps.coreHints` carry `appLevel: true`; the site badges them and `ideas.json` says so. They are listed rather than hidden because a plugin sometimes can.
- **Ranking:** `rank = demand * (1 - min(1, coverage / coveredAbove))`. Many likes with nothing similar comes first; anything that looks covered ranks 0 and is shown under "probably already covered" so a reader can disagree with the analysis.
- **Limits, stated on the Methodology page:** words are not meaning (a plugin can solve a request in different words, and two plugins can share words without doing the same thing), titles are short, and the forum is only one voice of the community.
- **ideas.json** (`schemas/ideas.schema.json`, validated every time it is written, written only when `--ideas` is given so tests never touch the committed file): top gaps with forum links as evidence, popular quiet plugins with directory/repository/issues links, and plugins archived by their authors. It contains no author names and carries `notes` explaining how to read it.
- **Committed forum data.** `data/forum/` is committed so the analysis is reproducible from the repository alone; the weekly workflow refreshes it and commits it back with the snapshot.

## Site (R4)

- **Tinta not found.** The brief says to use the "Tinta" design system if its tokens/CSS exist in the repo, but names no repository and none is visible to this session (the only repo in scope is this one). The site therefore uses a minimal, clean fallback: all colours, spacing and type live as CSS custom properties at the top of `site/assets/style.css` (`:root`, with the dark values redefined under `prefers-color-scheme: dark` and `data-theme="dark"`). Swapping in Tinta later means replacing that token block; no page markup refers to a colour.
- **Static HTML first, JSON second.** Every list page (This week, Growing, New, Looking for maintainers, Gaps, My plugins, Methodology) is rendered to plain HTML at build time, so it reads without JavaScript and the browser never has to compute anything. `app.js` is a small deferred enhancement: theme and language toggles, in-page list filtering, a lazy search page and the plugin page. No framework, no build step for the browser, no remote assets.
- **Plugin detail page = one JS shell + one small JSON per plugin.** 9,385 static pages would be 9,385 files to deploy and index for little gain; `plugin.html?id=<id>` fetches `p/<file>.json` (about 1-2 KB each, checked < 6 KB by score). The file name is the id with anything outside `[a-z0-9._-]` replaced by `_`, one function shared by the builder, the app and the link checker. Links are always relative so the site works under the GitHub Pages sub-path.
- **Search** loads `search.json` only on the search page (about 1 MB, 370 KB gzipped, ~100 bytes per plugin: id, name, downloads, weekly gain, category ids, keywords). It is never referenced from the other pages. Matching is plain substring on name, id, description keywords and a keyword-based category map (`lib/categories.mjs`, 20 categories), which is cheap, deterministic and explainable; the Methodology page says it is keyword matching and not semantic search.
- **Similar plugins** use the same TF-IDF vectors as the gap analysis (`lib/similar.mjs`), so "similar plugins" on a plugin page and the "closest plugins" on a gap card are the same notion of similarity. "My plugins" compares each plugin's weekly growth with the median of its similar plugins.
- **Language.** English is the source language. The Spanish toggle covers the interface and every page intro (107 keys in `lib/i18n.mjs`, a test fails if a key used by the pages is missing); the Methodology body stays in English and carries a Spanish summary at the top. That was the "cheap" toggle in the brief; translating the formulas would double the thing to keep consistent. Dynamic text is re-rendered through hooks on a language change instead of carrying `data-i18n` attributes.
- **No author names on the site**, except the owner's own "My plugins" page (`config.json`: `myAuthor`). The per-plugin JSON deliberately has no author field. Repository URLs still contain the owner handle (they are links to GitHub, not displayed names), and the tests compare visible text only. Maintainer candidates are framed as "looking for maintainers / room for an alternative" and the page states that this is not a judgement of the authors.
- **History honesty.** With one snapshot there is no growth to show. The site says so on the first screen ("First week of history ... History begins at <week>"), shows the biggest plugins and the estimated newcomers instead, and fills the growth lists as soon as a second weekly snapshot exists. While GitHub metadata is still pending (the rolling-refresh state of the first snapshot) the maintainer scores are labelled provisional.
- **Charts.** One series, one axis (downloads), 2 px line, ringed markers, crosshair + tooltip on hover/touch, and a "View as table" fallback. Drawn at the real pixel width and redrawn on resize so 11 px labels stay 11 px on a phone. Colour is a single blue pair validated for light and dark surfaces.
- **Determinism.** The site build takes "now" from the newest snapshot, writes files in sorted order and embeds no timestamp from the clock, so the same inputs give byte-identical output (score checks it). That also makes the weekly commit-back diff-minimal.
- **Checks that ship with the repo:** `scripts/check-links.mjs` (relative links, anchors, `plugin.html?id=` targets, no absolute paths, unique ids, https-only external links; externals are counted, never fetched) and `scripts/check-layout.mjs` (Playwright at 375 px and 320 px over every page plus plugin and search URLs: no horizontal scroll, no console errors, dark mode, search, chart tooltip, language toggle, filter). Playwright is deliberately not a dependency; it is resolved from node_modules or the global install, and CI installs it with `npm i --no-save playwright`.
